# Kranz 0.16

Kranz 0.16 adds typed parameters to actions and lets the TUI keep independent
lifecycle work moving in parallel. Existing actions remain valid: parameters
are opt-in and this release has no configuration migration.

## Declare typed inputs once

An action can declare checkboxes, choices, bounded numbers, and text. Each
value has an explicit projection into an argument, flag, position, environment
variable, or one of several option-specific fragments:

```yaml
actions:
  seed:
    argv: ["./seed.sh"]
    params:
      env:
        type: select
        options: [dev, staging, prod]
        default: dev
        arg: --env
      count:
        type: number
        default: 100
        min: 1
        max: 10000
        arg: --count
      write:
        type: checkbox
        default: false
        flag: --write
        confirm: This writes to the target environment
```

Parameterized actions execute an explicit `argv`; parameter values do not
become shell source. A value-dependent confirmation is part of the immutable
operation plan, including for interactive actions.

## Use the same contract everywhere

The TUI expands parameters below their action and opens a complete form with
`c`. CLI automation passes repeatable values, or deliberately omits one:

```bash
kranz actions run infra/seed \
  --param env=staging \
  --param count=250 \
  --param write=true \
  --confirm

kranz actions run infra/seed --no-param write
```

MCP clients use the typed `params` object on `action_run`; `null` has the same
explicit omission meaning. `kranz actions info OWNER/ACTION` and the MCP action
catalog expose the accepted types, defaults, constraints, projections, and
confirmation prompts.

See [Actions](../guide/actions) for the full contract and the
[runnable parameter example](../examples/action-parameters).

## Independent lifecycle operations

The dashboard can start, stop, or restart disjoint service sets at the same
time. Overlapping operations remain serialized, and a forced operation cancels
only overlapping work. This keeps an unrelated service responsive while a
different dependency chain is still starting.
